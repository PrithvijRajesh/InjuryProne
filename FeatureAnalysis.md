# Feature Analysis

## Interactive body model (Milestone 1)

**What it does:** User sees a front and back body diagram and clicks a muscle group (e.g. Hamstrings). The view zooms to a confirmation screen showing the selected group, ready to hand off to symptom questions.

**Why it matters:** This is the entry point to the whole app (PRD Core User Story). Every later step — symptoms, diagnosis, recovery guidance — depends on first getting a muscle-group selection here. Kept intentionally flat (one click, one confirmation) rather than adding a second "pick the exact muscle" step — simpler to use, and the symptom questions in the next feature can narrow things down instead.

**How it's built:**
- `src/data/muscleGroups.ts` — single source of truth. Each muscle group has a `view` (front/back) and an array of `shapes` (SVG polygons) that both draw its region on the body map and serve as its click target.
- The body isn't a photo — it's built entirely from polygons (`ShapeRenderer.tsx`), styled as one coherent faceted figure via a shared body-fill color and background-colored seams between facets. Adding a new group is a data change, not new artwork. The polygon coordinates are adapted from the open-source `react-body-highlighter` project (MIT License), which is why the body reads as a real anatomical diagram rather than a blocky placeholder.
- `App.tsx` swaps between the overview (`BodyMap`) and the confirmation view (`MuscleGroupDetail`) with a Framer Motion scale/fade transition — the "zoom into the muscle" effect from the original ask.

**History:** an earlier version of this feature zoomed into a second screen per group — a real anatomical reference image (Gray's Anatomy and similar public-domain atlases) with hand-placed hotspots for each individual muscle in the group, plus a "not sure / multiple areas" option. That was built out for all 13 groups, then removed after deciding it added a step without enough payoff for a "click where it hurts" flow — group-level selection is enough to hand off to symptom questions. The reference images (~6MB) and their hotspot data were deleted along with it rather than left unused.

## Symptom questions (Milestone 2)

**What it does:** After picking a muscle group, the user answers four categorized questions specific to that group — **where exactly** it hurts, **what it feels like**, **what makes it worse**, and **what activities** they do regularly — each with its own row of tappable chips, any number selectable per category. A "Continue" button stays disabled until at least one chip anywhere is picked.

**Why it matters:** This is PRD feature 2, and the bridge between "where does it hurt" and "what's the diagnosis" (feature 3). All four categories are tailored per muscle group (not shared lists) so the combination narrows toward an accurate diagnosis — e.g. for Knees, selecting "just below the kneecap" + "makes it worse: bending / running" + "activity: still a growing teen athlete" points specifically toward Osgood-Schlatter, something a flat, generic symptom checklist couldn't distinguish. The "activities you do" category exists specifically to capture that kind of context (sport/exercise pattern), not just the symptom itself. Language stays non-technical (e.g. "feels like it gives way" instead of "instability") so anyone can self-report without a medical background.

**How it's built:**
- `src/data/symptoms.ts` — `SYMPTOM_CATEGORIES_BY_GROUP`, keyed by the same muscle-group `id` used in `muscleGroups.ts`. Each group maps to 4 `SymptomCategory` entries (`location`, `painType`, `trigger`, `activity`), each with its own tailored `{ id, label }` option list.
- `MuscleGroupDetail.tsx` renders each category as a labeled section of toggle chips; selection state is `Record<categoryId, string[]>` so choices in different categories (and multiple choices within one category) are tracked independently. Continue is disabled only while every category is empty.
- Diagnosis logic isn't built yet — Continue currently just reveals a "coming in a later feature" placeholder, the same pattern used for the group-selection step before this one was built.

## Diagnosis with confidence (Milestone 3)

**What it does:** After answering symptom questions and clicking Continue, the user sees a ranked list of possible diagnoses for their muscle group, each with a High/Medium/Low confidence label, a one-line plain-language summary, and how many of that diagnosis's typical signs matched their answers. If nothing matches well, they see a fallback suggesting they see a doctor instead of a fabricated result.

**Why it matters:** This is PRD feature 3, and the payoff for the two features before it. The key design decision is scoring against **indicators** rather than authoring one diagnosis per exact combination of symptoms — with 4 categories and several options each, the number of possible combinations is far too large to enumerate by hand. Instead, each diagnosis lists the symptom options that point toward it, and any combination the user actually picks is scored against every diagnosis for that group by how many of its indicators were matched. This means: (1) every possible combination gets scored, not just ones someone thought to author in advance, and (2) two different combinations that both touch enough of the same indicators naturally land on the same diagnosis — e.g. for Knees, both "below the kneecap + bending + running/jumping + growing teen athlete" and a partial version of the same answers still point to Osgood-Schlatter, while swapping "growing teen athlete" for "running" shifts the top result to Patellar Tendinitis instead, without either combination being individually hard-coded.

Confidence is intentionally shown as a bucket (High/Medium/Low) rather than a precise percentage — this is a self-report tool built from a fixed set of hand-authored indicators, not a validated diagnostic test, so a number like "73%" would imply more precision than the underlying data supports.

**How it's built:**
- `src/data/diagnoses.ts` — `DIAGNOSES_BY_GROUP`, keyed by muscle-group id. Each diagnosis has an `indicators` map from `SymptomCategoryId` to the option ids (from `symptoms.ts`) that support it. `getDiagnosisMatches(groupId, selections)` scores every diagnosis in the group as `matchedIndicators / totalIndicators`, drops zero-match diagnoses, sorts by confidence (ties broken by raw matched count), and returns the top 4.
- `src/components/DiagnosisResults.tsx` + `.css` — renders the ranked cards, the confidence badge, the no-match fallback, and the disclaimer; reuses the app's existing panel/chip visual language.
- `MuscleGroupDetail.tsx` — Continue now computes matches from the current selections and swaps the symptom form for `DiagnosisResults`; "Back to symptoms" swaps back without clearing the selections, so revising answers doesn't force the user to start over.

**Verification note:** checked with a standalone script exercising the real scoring function against realistic symptom combinations (the Chrome browser extension wasn't available this session to click through the UI directly) — confirmed the Osgood-Schlatter vs. Patellar Tendinitis vs. Meniscus Tear cases above, plus that unmatched or empty selections correctly return no results.

## Body map sizing fix

**What it does:** The front and back body diagrams now render at the same physical size, and the "Body map adapted from..." credit line sits at the bottom of the screen instead of hugging the figures.

**Why it matters:** The back view's calves extend further down than any front-view content (data goes to y=2200 vs. front's ~1955 in the shared 1000-wide coordinate space), but both views shared a `viewBox` sized to only 2000 tall with `overflow: visible` — so the back figure's calves rendered outside the SVG's box, making the back figure look taller/longer than the front even though both used the same box.

**How it's built:**
- `src/data/muscleGroups.ts` — `OVERVIEW_VIEWBOX` height raised from 2000 to 2200 (the true max content height across both views), so nothing overflows and both figures occupy an identically-sized box.
- `BodyMap.css` — `.body-map-wrap` is a flex column with `justify-content: space-between` and a `min-height`, so the credit line is pushed toward the bottom of the screen instead of sitting immediately under the images.

## Recovery & prevention tips (Milestone 4)

**What it does:** Clicking a diagnosis card in the results list opens a dedicated recovery screen for that specific diagnosis: concrete recovery steps (e.g. icing windows, gentle mobility progressions), what to avoid while healing, ongoing prevention habits, and a "see a doctor if" callout for red-flag symptoms. A "Back to diagnoses" action returns to the same ranked list.

**Why it matters:** This is PRD feature 4 and the actual payoff of the whole flow — a ranked diagnosis by itself doesn't help someone recover; they need to know what to *do*. Content is deliberately generic and self-care-level (RICE-style guidance, gradual return-to-activity, standard prevention habits) rather than a clinical treatment plan, and every entry's "seek help if" section funnels anything serious toward "see a doctor or physical therapist" — matching the PRD's explicit scope limit of generic recommendations only, no specific providers or treatment directives.

**How it's built:**
- `src/data/recoveryPlans.ts` — `RECOVERY_BY_DIAGNOSIS_ID`, keyed by the same diagnosis `id` used in `diagnoses.ts`. Each entry is a `RecoveryPlan` with 4 string-array fields (`recoverySteps`, `avoid`, `preventionTips`, `seekHelpIf`) authored per diagnosis rather than shared/generic text, so a rotator cuff strain and a meniscus tear get meaningfully different guidance instead of interchangeable boilerplate.
- `src/components/RecoveryPlan.tsx` + `.css` — renders the 4 sections as cards reusing the app's existing panel/list visual language; the "seek help if" card gets an accent border to visually separate "self-care" from "this needs a professional."
- `DiagnosisResults.tsx` — diagnosis cards became clickable (`<button>` instead of `<div>`) with a new `onSelectDiagnosis` callback prop, so selecting a diagnosis is a first-class interaction rather than a dead-end display.
- `MuscleGroupDetail.tsx` — the old boolean `showResults` toggle became a 3-state `view` (`symptoms` | `results` | `recovery`) plus a `selectedMatch` field, so the flow is symptoms → results → recovery with each "back" action returning exactly one step rather than all the way to the start.

**Verification note:** cross-checked every diagnosis id in `diagnoses.ts` against the keys in `recoveryPlans.ts` with a standalone script — all 48 diagnoses across the 15 muscle groups have a matching recovery entry, none missing or orphaned. `tsc --noEmit` and `oxlint` both clean. The Chrome browser extension wasn't connected this session, so the click-through wasn't driven automatically — confirmed the dev server serves the app correctly and opened it in the default browser for manual review instead.

**Update — concreteness pass:** the first draft leaned on vague verbs ("reduce," "light," "gentle") that don't tell a user what to actually do. Rewrote every one of the 48 entries so each bullet names a specific exercise or stretch with sets/reps/hold time, a specific rest duration in days rather than "take it easy," and a specific return-to-activity threshold (e.g. a percent-per-week mileage increase) rather than "ease back in gradually." The goal: a user should be able to read any single bullet and know exactly what to do today, without interpreting what "light" or "reduce" means for them.

**Update — severity-scaled rest:** a flat day count (e.g. "rest 7-10 days") worked against the app's own purpose — it treats someone with barely-there soreness the same as someone with a much more significant version of the same injury, and never gives the "catch it early, back off for a couple days" guidance that the whole self-report flow is supposed to enable. Rewrote the first recovery-steps bullet for the 36 diagnoses that had a flat count into a two-branch structure: a short, specific recovery window for mild presentations (usually 2-3 days, or cutting activity volume by about half for overuse-type injuries) versus the fuller 5-10 day window for presentations that are sharp, limit normal movement, or show bruising/swelling. Diagnoses that already avoided flat rest windows (back-pain conditions, which modern guidance already treats as "stay gently active," plus cramps and posture-driven issues) were left unchanged. The three true red-flag diagnoses (tendon rupture, meniscus tear, sports hernia) kept firm "stop and see a doctor" language rather than severity branching, with an added note that mild-feeling pain doesn't reliably rule out something structurally significant for those specific injuries — severity self-assessment is the wrong tool there, unlike for a garden-variety strain or early tendinitis.

**Update — plain-language activities:** grouped activity phrases like "jumping and landing activity" or "change-of-direction activity" read as clinical shorthand rather than something a user could picture doing. Reworded 13 of these across the 48 entries to name the actual movement (specific examples in parentheses where useful — "jumping (box jumps, jump rope)," "explosive knee-drive movements (high kicks, quick sprint starts)") so every instruction reads as a concrete action rather than a category label.

## Telltale signs (diagnosis disambiguation)

**What it does:** Every diagnosis card in the results list now shows a highlighted "Telltale sign" line — one concrete, self-checkable detail that distinguishes it from the other diagnoses it commonly gets confused with in the same muscle group. For example, in Knees, Osgood-Schlatter's telltale sign is "a tender, sometimes visibly swollen bump right below the kneecap, in a still-growing teenager," while Patellar Tendinitis's is "a tender spot right below the kneecap that hurts most on landing from a jump" — same general location, different specific tell.

**Why it matters:** The scoring system in Milestone 3 can legitimately put 2-4 diagnoses in the same confidence band for one symptom combination, since it's intentionally not trying to force a single "correct" answer out of a self-report tool. But that left users with a list of similar-sounding conditions and no way to judge which one actually matches what they're feeling. Rather than add a whole extra disambiguating-question step to the flow (a bigger UI/logic change), the user chose the simpler, more direct fix: give each diagnosis one distinguishing physical detail right where they're already looking, on the results card itself.

**How it's built:**
- `src/data/diagnoses.ts` — added a required `telltaleSign: string` field to the `Diagnosis` type and the `diagnosis()` helper's signature (positioned between `summary` and `indicators`), then wrote one for all 48 diagnoses. Each is a specific, checkable physical detail (a location, a trigger, a visual sign) rather than a restatement of the summary — the summary explains what the injury *is*, the telltale sign is what you'd notice to tell it apart from a neighbor.
- `src/components/DiagnosisResults.tsx` + `.css` — renders it as a highlighted callout (accent-colored left border, "Telltale sign:" label) between the summary and the matching-signs count on every diagnosis card.

**Verification note:** confirmed all 48 `diagnosis()` call sites compile against the new 5-argument function signature — a missing `telltaleSign` argument would shift `indicators` into the wrong parameter and fail `tsc --noEmit`, which stayed clean. `oxlint` clean as well.

## Visual polish pass (body map alignment, brand mark, typography, palette)

**What it does:** Four pre-launch cosmetic fixes with no behavior change — the front and back body diagrams now render at the same visual height with no dead space under the front figure; both the "I" and "P" in "InjuryProne" are accent-colored instead of just the "I"; all text now uses Nunito with a deliberate size/weight hierarchy instead of a single oversized display treatment everywhere; and the dark theme uses a warmer near-black/near-white scale instead of a blue-tinted one.

**Why it matters:** This app's whole value is being usable in a moment of "something hurts, what is this" — visual polish here isn't decoration, it's what keeps the tool from reading as an unfinished student project right before it goes live on Vercel (**Current Focus**: cleaning up before publishing). The body-map mismatch in particular was a correctness-adjacent bug, not just an aesthetic one: because the back view's shape data legitimately extends further down (it includes the lower leg/feet; the front view's decorative calf shapes don't), sharing one `viewBox` height across both figures meant the front figure was scaled correctly but visually shorter, with an awkward gap between it and its "Front" caption.

**How it's built:**
- `src/data/muscleGroups.ts` — `OVERVIEW_VIEWBOX` (one shared height) became `VIEWBOX` (a `{ front, back }` record, each cropped to that view's real content bounds, computed by parsing every polygon's coordinates and taking the min/max). `BodyMap.tsx` looks up the right one per view instead of assuming a shared box.
- `BodyMap.css` — the `<svg>` sizing flipped from `width: min(42vw, 380px); height: auto` to `height: min(84vw, 460px); width: auto`. Because each view's `viewBox` now hugs its own content, sizing by height (a dimension both views share meaningfully) makes both figures fill their box edge-to-edge; sizing by width previously exposed the front view's shorter content as blank space instead.
- `App.tsx`/`App.css` — the heading text `InjuryProne` is now two `<span className="accent-letter">` wrappers (around "I" and "P") plus plain text, replacing a `::first-letter` CSS rule that structurally can only ever style one letter of a block, no matter how the text inside it is arranged.
- `index.html` + `src/index.css` — one Google Fonts request for Nunito (400/500/600/700/800) replaced the previous Bebas Neue + Inter pairing; `--font-display`/`--font-body` collapsed into a single `--font` variable, with hierarchy expressed through `font-weight` per element instead of switching typefaces (headings/section-titles 800, labels 600, body 400-500, the diagnosis match-count numbers 700 via `<strong>`). Every previously all-caps, wide-letter-spaced small label (figure captions, "Selected," confidence badges, etc.) was changed to normal-case SemiBold text. Section-title-style elements (the muscle group name, the diagnosis name) dropped from 32px to 24px, and the page `<h1>` dropped from a 40-64px responsive clamp to 28-34px, so no single screen leans on one oversized headline treatment.
- `src/index.css` `:root` — the six color tokens (`--bg`, `--bg-panel`, `--bg-elevated`, `--border`, `--text`, `--text-dim`) were the only place color was defined; every component already consumed color exclusively through these variables (confirmed via a repo-wide search for hardcoded `#000`/`#fff`/`black`/`white`, which found none), so updating the six hex values was sufficient to recolor the whole app.

**Verification note:** Chrome extension wasn't connected this session, so the flow was verified with a standalone Playwright script instead — screenshots of the body map (desktop 1000px and mobile 390px), the symptom picker, the diagnosis results, and the recovery screen, confirming equal-height front/back figures, both accent letters, the new type scale, and no raw black/white anywhere. `tsc --noEmit` clean.

**Update — actually drawing the front feet:** the equal-height fix above made both figures the same size, but sizing alone couldn't fix the real cause of the mismatch: the source `react-body-highlighter` polygon data simply never included a front-view foot — the back view's data runs to y=2200 (through the foot), the front view's stopped at y=1955 (the shin). Sizing two views to the same box just made a shin-height figure and a foot-height figure occupy equal-sized boxes; it didn't make them *look* like the same body. Fixed at the source instead: hand-authored a mirrored pair of foot polygons for `DECORATIVE_SHAPES.front` (`src/data/muscleGroups.ts`) that continue naturally from where the existing front calf shapes end, reaching the same depth (y≈2195) as the back view's feet, then set `VIEWBOX.front` back to the full 2200 height now that the content actually goes there. Also separately restored `.body-figure svg`'s sizing rule in `BodyMap.css` from a height-based cap back to the original `width: min(42vw, 380px)` — the earlier equal-height fix had substituted a smaller cap than the app shipped with, and the body map is the app's primary visual, not something to shrink for a secondary layout concern.

## Sports-medicine visual redesign (Milestone 5)

**What it does:** A ground-up visual redesign of every existing screen — same body map, same four symptom questions, same diagnosis cards, same recovery sections, same words throughout — but restyled to read as a purpose-built sports-medicine/PT product rather than a default dark-mode AI app. Layered gradient cards with real depth, a restrained red-accent ambient glow behind key sections, redesigned symptom chips and confidence indicators, and consistent hover/press micro-animations everywhere something is clickable.

**Why it matters:** The app's diagnostic content and flow were already solid (Milestones 1-4) — the gap was that flat dark backgrounds, gray borders, and pill-shaped everything read as generic/templated rather than trustworthy, which matters for a tool whose whole premise is "an athlete should trust this enough to act on it." The brief named specific references (Strava, Whoop, Nike Training Club) and an explicit anti-pattern list (no glassmorphism overload, no neon, no overly-rounded-everything, no empty dead space) — the design decisions below map directly to satisfying "premium and medically credible" without drifting into either generic-AI-dashboard or cyberpunk territory.

**How it's built:**
- `src/index.css` — the six flat color tokens became a small design system: translucent-white borders (`--border`/`--border-strong`) instead of flat gray hex, `--accent-deep`/`--accent-soft` as gradient/tint variants of the *same* existing red (no new hues added — the brief said keep the accent color), a 3-step radius scale, 3 layered shadow tokens, and one shared easing curve (`--ease`) used identically by CSS `transition`s and by the Framer Motion `transition` props in every screen's `.tsx` file, so hover states and page transitions move with the same feel. `body` got a fixed layered background (vertical dark gradient + two low-opacity blurred red radial gradients) replacing the flat `--bg` fill — this is the "subtle dark gradient instead of pure black" from the brief, applied once globally rather than re-implemented per screen.
- **Section-specific ambient glow** — rather than one glow reused everywhere (which the brief's "avoid excessive gradients" note was clearly warning against), each of `App.css` (header), `BodyMap.css` (behind the figures), `MuscleGroupDetail.css` (top of the symptom panel), and `DiagnosisResults.css` (behind the high-confidence card only) got its own local `::before` radial-gradient glow, scoped and low-opacity. All are `pointer-events: none` and add no new DOM nodes — purely `::before`/`::after`, so there's nothing for the click-handling logic to know about.
- **Cards** — `symptom-panel`, `diagnosis-card`, `recovery-section`, and `results-no-match` all moved from a flat single background color to a subtle top-to-bottom gradient between the existing `--bg-elevated`/`--bg-panel` tokens, picked up a real border + layered shadow, and (for the clickable `diagnosis-card`) a hover lift + shadow-intensify + `:active` press-down, all CSS-only.
- **Symptom chips** — `MuscleGroupDetail.css`: base shape moved from a 999px pill to an 8px-radius chip (the brief explicitly flagged "overly rounded elements everywhere" and "default pills" as things to avoid). The selected state — still driven by the exact same `symptom-chip--selected` class `MuscleGroupDetail.tsx` already toggled, no logic touched — now gets a red gradient fill, a glow shadow, and a `::before`-drawn checkmark, so a selection reads as a deliberate state rather than a color swap.
- **Data-driven confidence indicators** — `DiagnosisResults.tsx` got one small, careful addition: a `<div>` rendering a thin meter bar whose fill width is set from `match.confidence` (a real `0–1` ratio the scoring function in `diagnoses.ts` already computes — see Milestone 3) via a CSS custom property (`style={{ '--fill': match.confidence }}`) and `calc(var(--fill) * 100%)` in `DiagnosisResults.css`. This is presentational only — no new state, no new computation, `aria-hidden` since the existing text badge and "N of M matching signs" line already say the same thing to screen readers. The confidence badges themselves also gained a small leading indicator dot, filled for High, outlined for Medium, dim for Low — staying within the single red-accent palette rather than introducing a traffic-light green/amber/red scheme that would have broken the "keep the red accent" constraint.
- **Micro-animations** — symptom categories, diagnosis cards, and recovery sections each fade/slide in on mount with a slight stagger via CSS `@keyframes fade-in-up` + per-item `animation-delay`, no JavaScript involved. Hover/press states across chips, buttons, cards, and body-map hotspots (which also now get a subtle `scale(1.025)` on hover via `transform-box: fill-box`) all transition on the shared `--ease` curve for a consistent, "snappy but soft" feel rather than default browser easing.

**A bug caught mid-build, not after:** the first version of the symptom-category stagger used `.symptom-category:nth-child(n)`, which counts *all* siblings regardless of tag — but `.symptom-panel` renders three `<p>` tags (label, name, prompt) before the four `.symptom-category` divs, so `:nth-child(1)` through `:nth-child(3)` matched nothing, and the actual delays landed on the wrong categories. On a real mobile-width screenshot, two of the four categories were still invisible/mid-fade at a normal read speed. Fixed by switching to `:nth-of-type`, which counts only same-tag siblings and isn't affected by what precedes it. This is exactly the kind of bug that looks fine in a quick glance at one desktop screenshot but breaks on the actual page structure — worth calling out because it's a general risk with CSS list-stagger tricks (`:nth-child` vs `:nth-of-type` bites people constantly), not something specific to this app.

**Verification note:** walked the full flow (body map → symptom selection → diagnosis results with confidence meters → recovery plan) at both desktop (1200px) and mobile (390px) via Playwright screenshots, re-verifying after the `:nth-of-type` fix that all four symptom categories render correctly. Confirmed no text/copy changed anywhere by re-reading every screenshot against the pre-redesign wording. `tsc --noEmit`, `vite build`, and `oxlint` all clean.

## "AI slop" correction pass — precision/targeting design language

**What it does:** A second, more critical design pass on top of Milestone 5, prompted by being asked to evaluate the app the way an investor would: does this look AI-generated? It did — the Milestone 5 redesign had, ironically, reintroduced a different set of "generic AI product" tells (glow blobs, tracked-caps eyebrow labels, one repeated card recipe everywhere) even though it was a big improvement over the original flat dark UI. This pass replaces those specific patterns with a real, ownable creative direction instead of generic "premium dark app" decoration.

**Why it matters:** The prompt named the actual failure mode precisely: it's not that dark-mode-with-red-accent is wrong (the brief asked for exactly that), it's that *decoration disconnected from the product* is what reads as AI-generated — soft ambient glows, gradient progress bars, and pill badges are things every AI design tool reaches for by default because they're safe and generic, not because they mean anything for this specific app. An "InjuryProne" app's entire interaction model is *pinpointing a location on a body* — that's an unusually strong, specific, ownable visual metaphor (targeting/precision/clinical assessment) that the Milestone 5 pass never actually used. Leaning into it is what makes the difference between "a nice dark theme" and "a product with a point of view."

**How it's built:**
- **Two-typeface system** — added JetBrains Mono alongside the existing Nunito (`index.html`, `--font-mono` token in `index.css`), used exclusively for the app's "instrument" chrome: tag labels, step counters, captions, confidence percentages. This single change is a stronger "this was actually designed" signal than almost anything else in the pass, because a considered dual-typeface system (one humanist face for content, one mono face for data/UI) is specifically the kind of decision generic AI output doesn't make — it defaults to one friendly rounded sans-serif for literally everything.
- **Grid-texture background replaces glow blobs** — `index.css`'s `body` background dropped the two radial red gradients from Milestone 5 (the exact "AI landing page hero glow" pattern) for a faint 44px hairline grid (two 1px `linear-gradient`s at ~3% opacity) over the same dark vertical gradient. Reads as blueprint/graph-paper — technical and specific to a clinical-assessment feel, not a stock effect.
- **Reticle brand mark + viewfinder corner brackets** — a small CSS-only target ring+dot (`.brand-mark`) sits before the wordmark in `App.tsx`; four `aria-hidden` corner-bracket spans (`.frame-corner`, added in `BodyMap.tsx`) frame the body map like a camera viewfinder. Both are literal, not decorative-for-its-own-sake: the product's core action is targeting a point on a body, so the chrome says so.
- **Monospace `// tag` labels replace uppercase-tracked eyebrow text**, and **CSS-counter step numbers (`01`/`02`/`03`/`04`) replace the plain colored accent bar** on symptom categories and recovery sections (`MuscleGroupDetail.css`, `RecoveryPlan.css` — pure `counter-reset`/`counter-increment`/`content: counter()`, no JSX changes, so it automatically numbers however many categories a given muscle group actually has). Both read as "structured assessment form," which is what a PT/athletic-trainer-built tool should feel like — not startup-landing-page copy conventions.
- **Confidence meter became a segmented, flat-filled gauge with an exact numeric readout** instead of a smooth rounded gradient progress bar (`DiagnosisResults.css`/`.tsx`) — tick marks via `repeating-linear-gradient`, plus `{Math.round(match.confidence * 100)}%` rendered next to it in monospace. Reads as an instrument reading rather than a generic dashboard widget, while still using the exact same underlying `match.confidence` value the app already computed.
- **Diagnosis cards gained a large, near-invisible rank-numeral watermark** (`::after { content: counter(rank, decimal-leading-zero) }`) — an editorial ranked-list device that adds visual interest without adding any new text content; confirmed via a zoomed screenshot crop that it doesn't collide with the confidence badge in practice.
- **Selected symptom chips became solid-fill** (`var(--accent)` background, dark text) instead of translucent-gradient-plus-glow-shadow — a firmer, more confident "chosen" state, and one less place using the glow-shadow language.
- **Removed every colored/glow box-shadow and text-shadow app-wide** — cards, buttons, and big headings all lost their accent-tinted glow shadows in favor of plain neutral depth shadows (or none). The glow-everywhere look, on reflection, was itself one of the generic-AI tells this pass was correcting, so it had to go essentially everywhere it had been added in Milestone 5, not just in the header.

**A near-miss during verification, not an actual bug:** a Playwright screenshot showed one selected chip rendering with washed-out pink background and grey text, which looked exactly like a real rendering defect. It turned out to be the test script's own timing — the screenshot was captured while the chip's 0.2s CSS `background-color`/`color` transition was still interpolating, since the script clicked the second chip and screenshotted immediately with no settle time. Adding a short wait before the shot and recapturing confirmed both chips render identically once the transition finishes; nothing in the app itself was broken. Worth noting because it's a common false-positive shape when verifying CSS-transition-heavy UI with automated screenshots — always suspect the capture timing before the styles.

**Verification note:** re-walked the full flow (body map → symptoms → results → recovery) at desktop (1000-1200px) and mobile (390px) via Playwright, including a zoomed crop to check the rank-numeral watermark against the confidence badge and a re-shot with a settle delay to rule out the chip-transition false alarm above. `tsc --noEmit`, `vite build`, and `oxlint` all clean; confirmed no copy changed anywhere.
